# Being Seen

A serious game about gravitational lensing — and about how much of the universe
stays invisible until something bends the light our way.

Five pages, one narrative:

| Page | Question it answers |
|---|---|
| **Home** | 3D particle field of known lenses and unlit sources |
| **Lensing & SNe** | Can lensing make distant supernovae visible? |
| **Lensing & FRBs** | Can lensing copy FRB signals into multiple images? |
| **GW Lensing** | Can lensing correct black hole masses? |
| **Being Seen** | An anonymous guestbook where each story lights a star |

Built with Next.js (App Router), TypeScript, Three.js / react-three-fiber, and
Supabase for the guestbook.

**Deploying?** Follow [`DEPLOY.md`](DEPLOY.md) — it walks through Supabase and
Vercel click by click (in Chinese).

---

## Quick start

```bash
# macOS: this script works around a code-signing issue between the
# Apple-signed Node binary and the adhoc-signed SWC binary. See "Local dev
# on macOS" below.
./dev.sh install
cp .env.example .env.local   # optional: fill in to enable the guestbook
./dev.sh dev                 # http://localhost:3000
```

On Linux or Vercel, plain pnpm works:

```bash
pnpm install
pnpm dev
```

Inputs it expects in the repository root (they are large, so treat them as local

- `lenscat_catalog.csv` — 32,838 known lenses
- `chime_frb_catalog` — CHIME/FRB Catalogue 1 (VizieR fixed-width)

- `gISNe_sample.csv` — the five known lensed supernovae

`build_data.py` needs `numpy`, `pandas`, `matplotlib`, and `astropy` (only for
the FITS file). On this machine `/opt/anaconda3/bin/python` has all four.

## Deploying to Vercel

**Step-by-step instructions in Chinese: [`DEPLOY.md`](DEPLOY.md).**

Short version:

1. Push this repository to GitHub.
2. In Vercel, **Add New → Project** and import the repository. Next.js is
   detected automatically; `package.json` pins `pnpm@11.7.0` and Node 22.
3. Add the three environment variables (see below), then deploy.

`/` , `/lensing-supernovae`, `/lensing-frbs` and `/gravitational-wave-lensing`
are statically prerendered. `/being-seen` is statically prerendered too — it
reads stories from the browser — and `/api/stories` is server-rendered on
demand because it depends on the database.

### Repository weight

This repository tracks ~55 MB of research material that the website never
imports: `lensed_sn_mock.fits` (18 MB), `lenscat_catalog.csv` (3.6 MB), the
four notebooks, and the PDFs under `gISNe/` and the ZTF user guides. They make
every Vercel clone slow. If deploys feel sluggish they can be untracked with
`git rm --cached` (the local files stay on disk) — see `DEPLOY.md` §9.5.


## Connecting the guestbook (Supabase)

The guestbook is the only part that needs a backend. **The site deploys and
works without it** — the Being Seen page simply shows a notice instead of
accepting submissions.

1. Create a project at [supabase.com](https://supabase.com) (free tier is fine).
   Region: Singapore is the fastest from mainland China.
2. Open **SQL Editor** and run the whole of [`supabase/schema.sql`](supabase/schema.sql).
   The last statement prints a verification row — it must read
   `rls_enabled = true`, `policy_count = 1`, `policy_cmds = SELECT`.
3. Copy the credentials from **Project Settings → API Keys** and set:

| Variable | Used by | Notes |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | browser + server | project URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | browser | read-only reads |
| `SUPABASE_SECRET_KEY` | server only | writes; **never expose** |

Locally, put them in `.env.local` (git-ignored). On Vercel, add them under
**Settings → Environment Variables**.

### Security model

There are two write paths and they have materially different guarantees. The
first is the one the Vercel Git deployment uses; the second only applies if you
also run `supabase/schema-public-insert.sql`, which a static export needs
because it has no server to write with.

**Server path (recommended)**

- `stories` grants the `anon` role **SELECT only** — no INSERT, UPDATE or DELETE.
  A client holding the publishable key cannot write to the table at all.
- Writes go through `POST /api/stories`, which validates length, derives a
  hashed client identifier, and inserts with the secret key.
- A database trigger (`enforce_story_rate_limit`) caps each client at 20 stories
  per hour as a final backstop, plus a small in-memory limit per server instance.
- Only the story text, the star index and the rate-limit identifier are stored.
  No accounts, no names, no IP addresses — the identifier is a salted hash of
  IP and user agent, used solely for rate limiting.

**Static path (only with `schema-public-insert.sql`)**

That file grants `anon` INSERT on three columns. The database still enforces,
by column grant and `WITH CHECK`, that only `body`, `star_index` and
`client_hash` can be written — never `is_hidden`, `id` or `created_at` — and
that the body is 1–600 characters.

What you lose is real, and worth stating plainly:

- Anyone holding the publishable key can insert rows directly, bypassing the
  page entirely. The column grant and the length check bound the damage; they
  do not prevent spam.
- The 20-per-hour trigger is **not** an effective backstop on this path. It
  keys on `client_hash`, which here is a random token the browser generates and
  keeps in `localStorage`, so it can be cleared or forged at will. Verified
  against a mock PostgREST: the row that reached the database carried
  `client_hash: "web-uxzyrl331komv9rkp9i"`.
- The API route's validation and its in-memory limit never run.

If either of those matters, use the server path — which is why the Git
deployment is the recommended one and the static export is offered only as a
fallback for hosting that cannot run one.

## Local dev on macOS

`@next/swc-darwin-arm64` ships adhoc-signed (no Team ID). The Node binary from
the DSH runtime is Apple-signed, and macOS library validation refuses to load a
library with a different Team ID:

```
mapping process and mapped file (non-platform) have different Team IDs
```

`./dev.sh` solves this by making a copy of Node signed with
`com.apple.security.cs.disable-library-validation`. It also re-signs the native
SWC binary if its signature has been stripped. `/tmp/beingseen-node/node` is the
resulting dev binary.

None of this applies on Linux or on Vercel, which is why the project keeps a
plain `pnpm dev` path too.

## Verifying

`next build` passing does not mean the pages work. An R3F hook called outside
`<Canvas>` builds cleanly, typechecks cleanly, and then blanks the page for
every visitor. `./dev.sh smoke` opens all five routes in headless Chrome over
the DevTools protocol and checks two things.

**Rendering** — per route: no uncaught exception, no `console.error`, the
expected number of non-zero-sized canvases, no 3D scene stuck on its loading
placeholder, a non-empty `<h1>`, and no horizontal overflow when the viewport
is narrowed to a 390px phone.

**Accessibility semantics** — also per route, and free because it reuses the
same page loads: `lang`, exactly one `<h1>`, no skipped heading levels, every
image has `alt`, every button and link has an accessible name, every form
control has a label, and nothing that looks clickable (`cursor: pointer`) is
unreachable by keyboard. That last check is the one that matters most: it
catches the `<li onClick>` pattern, which is invisible to mouse users and
completely unusable for everyone else.

**Behaviour** — that the game's mechanics actually respond:
the detection-limit slider opens at the real ZTF limit and reports 0/5 without
lensing and 2/5 with it (the page's own headline), dragging it changes the
readout, the magnification slider reaches its win state ("Gap cleared") and
resets, clicking the starfield selects a star, and Tab reaches the
detection-limit slider with a visible focus ring.

**Degradation** — that each route survives having no WebGL, which is common on
managed and older machines. Without the guard in `clientOnly`, three.js throws
`Error creating WebGL context` and React unmounts the entire tree, so four of
the five pages became a blank error screen. Each route is re-loaded with
`getContext` stubbed to fail and must still have its heading, navigation, and
a substantial amount of body text.

**Reduced motion** — that the 3D scenes stop rotating themselves when the OS
asks for it, since perpetual motion in the visual field is what triggers
vestibular symptoms. Every scene used to spin forever, and the existing
`prefers-reduced-motion` block in CSS only covered CSS animations. Verified by
screenshotting a scene twice three seconds apart under an emulated
`prefers-reduced-motion: reduce` and requiring the two frames to be
byte-identical — plus a control run without the preference, which must differ.
Without that control the check could pass by being unable to see motion at all.

```bash
./dev.sh build
./dev.sh start      # keep running in another terminal
./dev.sh smoke      # exits non-zero if anything above fails
```

It is the only check here that can catch a client-side crash, and it earned its
place immediately — it caught exactly that bug on the Lensing & SNe page.
Without Chrome installed it prints a notice and skips.

## Corrections made to the original analysis

Two results from the earlier notebooks did not survive checking against the
underlying catalogues, and the site now reports the corrected versions.

**FRB candidates — the central claim was withdrawn.** The earlier analysis
reported two clean lensed candidates with dispersion-measure differences of 0.0
and 5.2 pc cm⁻³. That `dm_diff` column was never actually computed anywhere in
the notebooks, and the real catalogue values are **75.8** and **739.5**. Since
gravitational lensing does not change DM, neither pair can be two images of one
burst. A reproducible search over the 474 apparent non-repeaters finds 53 pairs
sharing a position, of which only 3 survive even a lenient DM tolerance — and
none satisfies both requirements. The page therefore presents a null result.

**Gravitational-wave mass correction — the formula was wrong.** The earlier code
computed `m_corr = m_obs / μ`, which reduces to `45²/m_obs` and is not a mass at
all. The standard relation is `m_obs = m_true·√μ`. Because a single lens applies
one magnification to every image, the mass ratio must be preserved, so both
masses are divided by the same `√μ`. Corrected masses become 45.0 / 32.4 M☉ and
45.0 / 35.3 M☉, and the page states plainly that this is a hypothesis test —
the magnification that *would* be required — not a measurement.
