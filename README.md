# Being Seen

A serious game about gravitational lensing — and about how much of the universe
stays invisible until something bends the light our way.

Five pages, one narrative:

| Page | Question it answers |
|---|---|
| **Home** | 3D particle field of known lenses and unlit sources |
| **Lensing & SNe** | Can lensing make distant supernovae visible? |
| **Lensing & FRBs** | Can lensing copy FRB signals into multiple images? |
| **GW Lensing** | Can lensing correct black hole masses? |
| **Being Seen** | An anonymous guestbook where each story lights a star |

Built with Next.js (App Router), TypeScript, Three.js / react-three-fiber, and
Supabase for the guestbook.

**Deploying?** Follow [`DEPLOY.md`](DEPLOY.md) — it walks through Supabase and
Vercel click by click (in Chinese).

## Quick start

```bash
# macOS: this script works around a code-signing issue between the
# Apple-signed Node binary and the adhoc-signed SWC binary. See "Local dev
# on macOS" below.
./dev.sh install
cp .env.example .env.local   # optional: fill in to enable the guestbook
./dev.sh dev                 # http://localhost:3000
```

On Linux or Vercel, plain pnpm works:

```bash
pnpm install
pnpm dev
```

`frb_candidate_filtering.png` shows the same funnel as the interactive one on

## Deploying to Vercel

**Step-by-step instructions in Chinese: [`DEPLOY.md`](DEPLOY.md).**

Short version:

1. Push this repository to GitHub.
2. In Vercel, **Add New → Project** and import the repository. Next.js is
   detected automatically; `package.json` pins `pnpm@11.7.0` and requires
   Node >= 22, which is what Vercel will pick.
3. Add the three environment variables (see below), then deploy.

`/` , `/lensing-supernovae`, `/lensing-frbs` and `/gravitational-wave-lensing`
are statically prerendered. `/being-seen` is statically prerendered too — it
reads stories from the browser — and `/api/stories` is server-rendered on
demand because it depends on the database.

### Repository weight

Measured, not estimated: the tip of `main` holds **88.5 MB** of file content,
of which **87.2 MB is material the site never imports** — the paper PDFs under
`gISNe/` (47.6 MB), the `.fits` simulation (18.4 MB), the two ZTF user guides
(9.0 MB), `lenscat_catalog.csv` (3.7 MB), the notebooks (4.9 MB), several
root-level analysis figures the site does not display, and
`BeingSeen计划.docx`. Everything the site actually builds from — `src/`,
`public/`, `scripts/`, `supabase/` and the config files — comes to **1.35 MB**.

An earlier version of this section said these could be untracked with
`git rm --cached` to speed up Vercel clones. That is half right, and the
distinction matters:

- **Vercel does a shallow clone** (`--depth 1`), which fetches only the tip
  tree. Untracking the files would drop what it downloads from 88.5 MB to
  about 1.35 MB, so for deploy time the advice holds.
- **A normal `git clone` would not get smaller at all.** Every one of those
  files was added in a single commit and never modified, so all 89.2 MB of
  blobs stay reachable from history. Shrinking that needs a history rewrite
  (`git filter-repo` or BFG plus a force push), which would rewrite every
  commit hash and break anyone's existing clone — not something to do casually.

`.gitignore` was written as though these files were never meant to be tracked,
and the section above calls them local data. Making that true for the tip is a
one-command change; say the word and it can be done, or the files can stay as
they are, since a shallow clone of this size is not actually a problem.

### Installed dependencies

Two `devDependencies` exist only for the macOS build workaround, and they are
not equally expensive, which is worth knowing before anyone tries to trim them:

- `@next/swc-darwin-arm64` is 86 MB installed, but its manifest declares
  `os: ["darwin"]` and `cpu: ["arm64"]`, so npm and pnpm skip it on Linux. A
  Vercel install never fetches it. Leaving the entry in place costs nothing, and
  removing it would only risk the local macOS path.
- `@next/swc-wasm-nodejs` is 29 MB and declares no platform constraints, so it
  *is* installed on Linux, where it can never be used — it is the fallback for
  when a native SWC binary will not load, which only happens here because of
  the macOS code-signing situation. It is kept because removing it would mean
  re-testing that fallback on a Mac, and 29 MB is not worth that risk.

`next` already lists every platform binary as an `optionalDependency`, so in
principle the direct darwin entry is redundant; it is pinned because
`pnpm-workspace.yaml` excludes that exact version from the supply-chain age
check.


## Connecting the guestbook (Supabase)

The guestbook is the only part that needs a backend. **The site deploys and
works without it** — the Being Seen page simply shows a notice instead of
accepting submissions.

1. Create a project at [supabase.com](https://supabase.com) (free tier is fine).
   Region: Singapore is the fastest from mainland China.
2. Open **SQL Editor** and run the whole of [`supabase/schema.sql`](supabase/schema.sql).
   The last statement prints a verification row — it must read
   `rls_enabled = true`, `policy_count = 1`, `policy_cmds = SELECT`.
3. Copy the credentials from **Project Settings → API Keys** and set:

| Variable | Used by | Notes |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | browser + server | project URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | browser | reads; **also writes** on the static path |
| `SUPABASE_SECRET_KEY` | server only | writes; **never expose** |
| `NEXT_PUBLIC_SITE_URL` | server (build) | optional; absolute URL for link previews |

Locally, put them in `.env.local` (git-ignored). On Vercel, add them under
**Settings → Environment Variables**.

### Security model

There are two write paths and they have materially different guarantees. The
first is the one the Vercel Git deployment uses; the second only applies if you
also run `supabase/schema-public-insert.sql`, which a static export needs
because it has no server to write with.

**Server path (recommended)**

- `stories` grants the `anon` role **SELECT only** — no INSERT, UPDATE or DELETE.
  A client holding the publishable key cannot write to the table at all.
- Writes go through `POST /api/stories`, which validates length, derives a
  hashed client identifier, and inserts with the secret key.
- A database trigger (`enforce_story_rate_limit`) caps each client at 20 stories
  per hour as a final backstop, plus a small in-memory limit per server instance.
- Only the story text, the star index and the rate-limit identifier are stored.
  No accounts, no names, no IP addresses — the identifier is a salted hash of
  IP and user agent, used solely for rate limiting.

**Static path (only with `schema-public-insert.sql`)**

That file grants `anon` INSERT on three columns. The database still enforces,
by column grant and `WITH CHECK`, that only `body`, `star_index` and
`client_hash` can be written — never `is_hidden`, `id` or `created_at` — and
that the body is 1–600 characters.

What you lose is real, and worth stating plainly:

- Anyone holding the publishable key can insert rows directly, bypassing the
  page entirely. The column grant and the length check bound the damage; they
  do not prevent spam.
- The 20-per-hour trigger is **not** an effective backstop on this path. It
  keys on `client_hash`, which here is a random token the browser generates and
  keeps in `localStorage`, so it can be cleared or forged at will. Verified
  against a mock PostgREST: the row that reached the database carried
  `client_hash: "web-uxzyrl331komv9rkp9i"`.
- The API route's validation and its in-memory limit never run.

If either of those matters, use the server path — which is why the Git
deployment is the recommended one and the static export is offered only as a
fallback for hosting that cannot run one.

## Local dev on macOS

`@next/swc-darwin-arm64` ships adhoc-signed (no Team ID). The Node binary from
the DSH runtime is Apple-signed, and macOS library validation refuses to load a
library with a different Team ID:

```
mapping process and mapped file (non-platform) have different Team IDs
```

`./dev.sh` solves this by making a copy of Node signed with
`com.apple.security.cs.disable-library-validation`. It also re-signs the native
SWC binary if its signature has been stripped. `/tmp/beingseen-node/node` is the
resulting dev binary.

None of this applies on Linux or on Vercel, which is why the project keeps a
plain `pnpm dev` path too.

## Verifying

`next build` passing does not mean the pages work. An R3F hook called outside
`<Canvas>` builds cleanly, typechecks cleanly, and then blanks the page for
every visitor. `./dev.sh smoke` opens all five routes in headless Chrome over
the DevTools protocol and runs four passes over them.

**Rendering** — per route: no uncaught exception, no `console.error`, the
expected number of non-zero-sized canvases, no 3D scene stuck on its loading
placeholder, a non-empty `<h1>`, and no horizontal overflow when the viewport
is narrowed to a 390px phone.

**Accessibility semantics** — also per route, and free because it reuses the
same page loads: `lang`, exactly one `<h1>`, no skipped heading levels, every
image has `alt`, every button and link has an accessible name, every form
control has a label, and nothing that looks clickable (`cursor: pointer`) is
unreachable by keyboard. That last check is the one that matters most: it
catches the `<li onClick>` pattern, which is invisible to mouse users and
completely unusable for everyone else. The same pass measures text contrast
against the real composited background and requires WCAG AA (4.5:1, or 3:1 for
large text), and requires a `link[rel=icon]` and an absolutely addressed
`og:image`.

**Behaviour** — that the game's mechanics actually respond:
the detection-limit slider opens at the real ZTF limit and reports 0/5 without
lensing and 2/5 with it (the page's own headline), dragging it changes the
readout, the magnification slider reaches its win state ("Gap cleared") and
resets, clicking the starfield selects a star, and Tab reaches the
detection-limit slider with a visible focus ring.

**Degradation** — that each route survives having no WebGL, which is common on
managed and older machines. Without the guard in `clientOnly`, three.js throws
`Error creating WebGL context` and React unmounts the entire tree, so four of
the five pages became a blank error screen. Each route is re-loaded with
`getContext` stubbed to fail and must still have its heading, navigation, and
a substantial amount of body text.

**Reduced motion** — that the 3D scenes stop rotating themselves when the OS
asks for it, since perpetual motion in the visual field is what triggers
vestibular symptoms. Every scene used to spin forever, and the existing
`prefers-reduced-motion` block in CSS only covered CSS animations. Verified by
capturing three frames two seconds apart under an emulated
`prefers-reduced-motion: reduce` and requiring all three to be byte-identical —
plus a control run without the preference, which must differ. Without that
control the check could pass by being unable to see motion at all; three frames
rather than two because the home starfield's `PerformanceMonitor` occasionally
changes the canvas resolution, which made a two-frame version flaky.

```bash
./dev.sh build
./dev.sh start      # keep running in another terminal
./dev.sh smoke      # exits non-zero if anything above fails
```

It is the only check here that can catch a client-side crash, and it earned its
place immediately — it caught exactly that bug on the Lensing & SNe page.
Without Chrome installed it prints a notice and skips.

## Fidelity to the brief

`./dev.sh outline` is a separate check because it answers a different question:
not "is the site broken" but "does it do what `网页布局纲要.docx` asked for". It
turns every requirement in the brief — the five pages and their order, the fixed
navigation, the dark palette, each page's headline copy verbatim, each named
chart and its interactivity — into an assertion against the running site, and
reports 41 of them.

```bash
./dev.sh outline    # exits non-zero if any requirement is unmet
```

One of the 38 is not from the brief. W6 guards an arithmetic property the page
had got wrong: the required magnification is derived by assuming the true mass
sits on the 45 M☉ boundary, so a strict `<` comparison against that boundary
could only ever report "no" — a tautology dressed as a result. W6 asserts both
that the data actually puts the mass at or below the boundary and that the page
says so.

It normalises typographic quotes and dashes before comparing: the pages use
’ ‘ “ ” and —, the brief is plain text, and without that step the check reports
false failures on text that is in fact identical.

### The database layer

`./dev.sh db-check` runs `supabase/schema.sql` and
`supabase/schema-public-insert.sql` against a real Postgres — PGlite, Postgres
compiled to WebAssembly — and asserts what they claim: RLS is on, the anon role
gets SELECT and nothing else, the trigger stops the 21st story from one client
with SQLSTATE P0001 (the code the API route turns into a 429), `is_hidden` rows
are invisible to anon, and after the second file the anonymous write path can
reach only the three permitted columns and nothing outside the `WITH CHECK`
bounds.

It needs one optional dependency, deliberately not in `devDependencies` so it
does not add to every Vercel install:

```bash
pnpm add -D @electric-sql/pglite   # one-off
./dev.sh db-check
```

Without it the script prints a notice and exits 0. Running it is what found
that `schema-public-insert.sql` did not execute at all — it closed with a query
against `pg_policy.cmd`, a column that does not exist (the system table calls it
`polcmd`), and because the file is submitted as one query Postgres wraps it in
an implicit transaction: the error rolled back the grant and the policy with it,
so the file looked applied and changed nothing.

It also covers a bug that only a real Supabase project could expose. New
projects are advised to switch "Automatically expose new tables" off, and with
it off a newly created table gets no grants at all — not even for
`service_role`. `schema.sql` granted SELECT to `anon` explicitly but assumed
`service_role` kept the defaults, so the result on a live project was that
anonymous reads worked and the server could not write: `42501 permission denied
for table stories`. The grant is now explicit, wrapped in a role check so the
file still runs end to end on a bare Postgres. Local PGlite could not have
found this, because the test creates those roles itself rather than inheriting
Supabase's default-privilege setup — the live project did.

It also covers the two claims that are easy to state and hard to trust, and
established both by running them:

- **Re-running `schema.sql` returns the table to the locked-down baseline.**
  `revoke all` on a table also removes column-level grants, which is not
  obvious, so the anonymous write access that `schema-public-insert.sql` opens
  is closed again by re-running the first file. That file now also drops the
  INSERT policy rather than leaving a dormant one behind. (The first version of
  this check asserted the opposite — that the column grant would survive — and
  the test corrected me.)
- **The realtime block takes a different branch on Supabase than on a bare
  Postgres.** Supabase pre-creates the `supabase_realtime` publication, so the
  `alter publication ... add table` path runs — the one live story updates
  depend on. Earlier runs only ever exercised the exception fallback. Both
  branches are covered now, and re-running does not add the table twice.

Three places deliberately differ from the brief, and the script prints them
alongside the result rather than hiding them:

- **The FRB candidate chart.** The brief asks for `time_delay_histogram.png`, a
  distribution of the candidates' time delays. That chart was built around the
  two "clean candidates" whose existence the analysis does not support. Plotting
  the time delays of candidates that are not candidates would be misleading, so
  the page shows the DM-versus-separation scatter instead — which is the actual
  evidence for the null result.
- **The GW mass chart.** The brief names `mass_correction_with_errors.png`,
  produced with `m_corr = m_obs / μ`. That is not a mass; the page regenerates it
  as `gw_mass_correction.png` from `m_obs = m_true·√μ`, still with error bars.
- **Guestbook storage.** The brief specifies Firebase; the project requires
  Supabase.

## Corrections made to the original analysis

Two results from the earlier notebooks did not survive checking against the
underlying catalogues, and the site now reports the corrected versions.

**FRB candidates — the central claim was withdrawn.** The earlier analysis
reported two clean lensed candidates with dispersion-measure differences of 0.0
and 5.2 pc cm⁻³. That `dm_diff` column was never actually computed anywhere in
the notebooks, and the real catalogue values are **75.8** and **739.5**. Since
gravitational lensing does not change DM, neither pair can be two images of one
burst. A reproducible search over the 474 apparent non-repeaters finds 53 pairs
sharing a position, of which only 3 survive even a lenient DM tolerance — and
none satisfies both requirements. The page therefore presents a null result.

**Gravitational-wave mass correction — the formula was wrong.** The earlier code
computed `m_corr = m_obs / μ`, which reduces to `45²/m_obs` and is not a mass at
all. The standard relation is `m_obs = m_true·√μ`. Because a single lens applies
one magnification to every image, the mass ratio must be preserved, so both
masses are divided by the same `√μ`. Corrected masses become 45.0 / 32.4 M☉ and
45.0 / 35.3 M☉, and the page states plainly that this is a hypothesis test —
the magnification that *would* be required — not a measurement.
